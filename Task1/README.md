# Задание 1. Проектирование технологической архитектуры

Компания хочет сделать упор на развитие в регионах РФ. Планируется значительный рост количества пользователей и запросов. Нужно обеспечить бесперебойную работу сервиса 24/7, при этом сервис должен обслуживать клиентов из всех часовых поясов.

Требования к отказоустойчивости системы крайне высокие: RTO — 45 мин., RPO — 15 мин. Согласно требованиям бизнеса, доступность приложения должна быть равна 99,9%.

Дополнительно к этому нужно обеспечить одинаковое время загрузки страниц для пользователей из разных регионов. Оно не должно зависеть от географического местоположения пользователя.

**1. Стратегия масштабирования**

Согласно описанию задачи: core-app — монолитное бэкенд-приложение. В описании нет информации - могут ли быть проблемы с его масштабированием (монолит как правило масштабируется хуже, может потребоваться доработка) + также нет информации о потребляемых ресурсах. Будем считать, что проблем с горизонтальным масштабированием нет (можно развернуть N инстансов приложения).  Остальные приложения разработаны в рамках микросервисной архитектуры и по-умолчанию считаем, что нет проблем с горизонтальным масштабированием. Так как нет информации о потребляемых ресурсах, то предположим, что поды утилизируются полностью и нет необходимости в вертикальном масштабировании. Применим стратегию горизонтального масштабирования + кластерное масштабирование - при росте нагрузки разворачиваются дополнительные инстансы подов + при превышении ресурсов кластера, новый инстанс кластера.

Так как нужно обеспечить одинаковое время загрузки страниц для пользователей из разных регионов, то потребуется использовать георезервирование, т.е. нужно создать дополнительные зоны безопасности, куда будут перенаправляться запросы по признаку местоположения.

**2. Конфигурация kubernetes**

Так как доступность сервисов должна быть обеспечена для разных регионов, которые располагаются в разных часовых поясах, то расстояния между ЦОД могут быть значительными (Московский часовой пояс (может быть несколько ЦОД - Север/Юг/Центр так как большие нагрузки) + Сибирь + Дальний восток). В связи с этим необходимо использовать несколько независимых кластеров kubernetes (свой в каждом ЦОД) - такой подход независим от сетевой связанности между ЦОД и от внутренних недостатков фейловер-механизмов в Kubernetes.

**3. Балансировка нагрузки**

Балансировку нагрузки выполним при помощи GSLB (global server load balancing). В случае падения соединения или полного отказа ЦОДа сервис GSLB перенаправит пользователей к доступному дата-центру.

**4. Фейловер стратегия**

Фейловер стратегию выберем в соответствии с требованиями - доступность приложения должна быть равна 99,9%. Для выполнения данного требования подходит стратегия Active-Active.

**5. Конфигурация БД.**

Имеющийся инстанс БД перенесем в кластер Patroni, настроим георезервирование и репликацию.
